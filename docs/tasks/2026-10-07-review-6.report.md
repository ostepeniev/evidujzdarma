## Коміт `62f07a1` — R9.1 (A1): квартантин із невалідною датою

1. **Коміти:** `62f07a1`.
2. **Було → стало:**
   - `lib/server/lifecycle.ts:114` (`PRODUCTION_QUARANTINE`): `case when soldAt ~ <regex> then soldAt::timestamptz >= eet_mode_changed_at else true end` → `case when soldAt ~ <regex> and pg_input_is_valid(soldAt, 'timestamptz') then … else true end`.
   - Невалідна дата тепер іде в гілку `else true`, тобто рядок вважається можливою ostrou tržbou (fail-closed, як і обіцяв коментар).
   - **Інших місць, де дату з payload перетворюють у SQL, немає.** Пошук `::timestamptz`, `::date`, `to_timestamp` по `apps/` і `packages/`:
     - `fiscal.ts:248` бере серверний `now`;
     - `catalog.ts` і `worker/import-res.ts` беруть дати з ARES/RES, а не з payload каси.
   - **Міграцій немає.** Наявні дані: на проді 7. 10. відкритого квартантину 0 (розділ «Деплой» рецензії).
3. **Гейти, що були червоними** (`test/integration/r9-1-quarantine-bad-date.test.ts`). Production-акаунт, два відкриті рядки квартантину з payload у старому режимі (`mode: "mock"`): `0000-01-01T00:00:00Z` (TOO_OLD) і `2026-10-07T99:99:99Z` (INVALID). До виправлення тест падав на `closeAccount(…, {confirm: true})` з `date/time field value out of range: "0000-01-01T00:00:00Z"` (з `unsentProductionOf` у `sendClosedSummary`). Після виправлення:
   - `accountState` живого акаунту працює;
   - `closeAccount` без підтвердження дає 409, з підтвердженням працює;
   - обидва рядки потрапляють в `unsentProductionOf`, а в `accountState` після закриття `quarantineProduction = 2`;
   - `runRetention(+31 d)` працює: `accountsHeld = 1`, акаунт тримається, інший закритий акаунт (mock) видалено;
   - `settleElsewhere` через `seen` (шлях із `PRODUCTION_QUARANTINE` в UPDATE) закриває обидва рядки.

   `pnpm -r test` (web 499), `pnpm -r typecheck` — зелені.
4. **Самостійні рішення:** регулярний вираз лишив перед `pg_input_is_valid`, щоб дата без часової зони не залежала від `TimeZone` сесії.
5. **Що не вдалося:** —.

## Коміт `376a951` — R9.2 (A2), R9.5 (A5), R9.6 (A6)

1. **Коміти:** `376a951`.
2. **Було → стало:**
   - **R9.2:** у `lib/server/lifecycle.ts:248` (`settleElsewhere`, шлях `seen`) `lte(received_at, lastSeen)` і `lte(updated_at, lastSeen)` замінено на `date_trunc('milliseconds', col) <= lastSeen` (helper `seenBy`). Використання: `:253` (sales) і `:275` (квартантин). Шлях `ids` не змінювався.
   - **R9.5:** у `lifecycle.ts:157-158` (`unsentView`) `Math.max(0, ...rows)` замінено на `reduce`.
     - Інші розгортання `Math.max/min(...)`: `closings.ts:156-157` (уzávěrky одного рахунку за період, це сотні рядків) і `fiscal-core/p12.ts:181` (ітерації PBKDF у .p12, одиниці). Вони не ростуть із кількістю тржб, тож лишив.
   - **R9.6:** у `lib/server/quarantine.ts:96-102` (`notifyClosedUnsent`) `max(...)::text` + `replace` + `Date.parse` замінено на `floor(extract(epoch from max(...)) * 1000)::bigint::text`. Пізніший із двох часів береться через `reduce`.
     - Формат ключа той самий (мілісекунди), тож ключі, уже записані в `email_outbox` на проді, збігаються.
   - **Міграцій немає.**
3. **Гейти, що були червоними** (`test/integration/r9-2-settle-precision.test.ts`):
   - **R9.2.** Закритий production-акаунт: 3 продажі з `received_at` і 1 рядок квартантину з `updated_at` (явний `timestamptz` із 6 знаками). `accountState` → `seen` → один `settleElsewhere(seen)` повертає `{sales: 3, quarantine: 1}`, і нічого не лишається.

     - Було: `RangeError: Maximum call stack size exceeded`.
   - **R9.6.** Після «Evidováno jinak» сесія PG переходить на `DateStyle = 'SQL, DMY'` і `TimeZone = 'America/New_York'`, і каса довозить тржбу. Ключ `closed-unsent:` не містить `NaN` і містить час останнього «Evidováno jinak» у мс з `extract(epoch …)`.
     - Було: ключ із `NaN`.

   `pnpm -r test` (web 502), `pnpm -r typecheck` — зелені.
4. **Самостійні рішення:** час для ключа округлюється донизу (`floor`), як раніше це робив `Date.parse`, тож ключі на проді лишаються сумісними.
