# Звіт кодової сесії за рецензією №2 (блок R5 і решта R4)

## Що вже є (з прочитаного коду на `e245901`, 2. 10. 2026)

Перед кодом звірив з кодом знахідки рецензії; усі підтвердилися.

- **Якорі довіри.** `packages/fiscal-core/src/eet2/response.ts:84-87` для production бере NCA Root CA/RSA 10/2023 → NCA SubCA2/RSA 12/2023 (`trust-anchors.ts`, файли з ruby-eet2). Для Playground — I.CA.
- **Режим каси.** `sale-factory.ts:46,67` бере режим тржби з кешованого `config.account.mode`. `server/sales.ts:128` приймає `input.mode` без звірки з режимом акаунта.
- **Класифікація помилок.** `client.ts:143` класифікує `Chyba` як `retryable = code < 0`. `INVALID_RESPONSE` після трьох спроб ставить `next_attempt_at +365 d` (`fiscal.ts:338`).
- **Оплати.** `voucher` — єдиний спосіб для poukazů, stravenek і kreditu: іде в `cerp_zuct` і в `celk_trzba` (`sale.ts:7,23,160`).
- **Середовище сертифіката** визначається за словом «playground» у назві видавця (`certificates.ts:14`).
- **Typecheck.** У `apps/web` `typecheck` = `tsc --noEmit`, без `next typegen`.
- **Решта** (схвалення vratky без прив'язки, EIČ ≠ CN, опитування `rejected`, закриття акаунта, кеш ARES) — як описано в додатку A-fiscal-r2, В-1…В-5, і в B Н2-1. Кожен пункт звіряю з кодом перед своїм комітом.

## Коміт `5374f0b` — R5.2 (якорі довіри production = I.CA)

1. **Коміти:** `5374f0b`.
2. **Було → стало:**
   - `packages/fiscal-core/src/eet2/response.ts` (`defaultTrustPolicy`):
     - **Було:** production — NCA Root CA/RSA 10/2023 → NCA SubCA2/RSA 12/2023. Відповідь, підписана за документацією FS, з першої ostré тржби стала б `INVALID_RESPONSE`.
     - **Стало:** обидва середовища — I.CA Root CA/RSA 05/2022 → I.CA Public CA/RSA 06/2022. Середовища розрізняються лише тестовими ознаками відповіді (`test`, POK `-ff`); ця перевірка вже була (`response.ts`, кінець `verifyResponse`).
   - **Пін GFŘ** (`NTRCZ-72080043` + keyUsage) лишився. У коментарі записано, що для production його не підтверджено, перевірити на першій ostré відповіді, а запобіжником буде R5.4.
   - **`trust-anchors.ts`:** константи `icaIntermediate` і `icaRoot` замість чотирьох. Файли переміщено в `official/response-trust/ica/`, файли NCA з репозиторію видалено.
   - **`official/README.md`:** джерело — «Přístupové a provozní informace – produkční prostředí» v1.1 (10. 7. 2026), kap. 3.3, дата перевірки 2. 10. 2026 (рецензія №2, Т8). Окремо записано, що ověřovací mód підпис не перевіряє.
   - **Міграцій немає.** Даних це не стосується: production-тржб ще немає.
3. **Гейти, що були червоними** (`packages/fiscal-core/test/eet2.test.ts`):
   - production-ланцюжок = I.CA: тест падав з `expected 'CN=NCA SubCA2/RSA 12/2023…' to match /CN=I\.CA Public CA\/RSA 06\/2022/`;
   - справжня відповідь Playground під production-політикою проходить ланцюжок і пін і відкидається лише через тестові ознаки: тест падав з reason `"podpisový certifikát nevydala očekávaná CA"` замість `"produkční odpověď má testovací příznaky"`.

   Тепер обидва зелені. Тест відповідності вбудованих констант файлам оновлено (2 якорі замість 4).
4. **Самостійні рішення:**
   - Файли NCA видалено з `official/`, а не лише з політики, щоб ніщо не виглядало як «друга довірена CA». Вони лишаються в історії git.
   - Каталог `playground/` перейменовано на `ica/`, бо ті самі файли тепер обслуговують і production.
5. **Що не вдалося:** підпис production-відповіді неможливо перевірити заздалегідь, бо ověřovací mód повертає непідписану `Chyba 0`. Звірка на першій ostré відповіді — після R5.4.

## Коміт `78f8230` — R5.1 (MODE_MISMATCH: каса з кешованою конфігурацією не продає «mock» після переходу в production)

1. **Коміти:** `78f8230`.
2. **Було → стало:**
   - **Схема:** нова колонка `accounts.eet_mode_changed_at` (`timestamptz NOT NULL DEFAULT now()`), міграція `0016_mode_changed_at.sql`. **Наявні дані:** усі наявні акаунти отримують час міграції як момент перемикання. Тож тржби, продані до деплою, лишаються у своєму режимі (стара поведінка), а невідповідність після деплою йде в карантин.
   - `lib/server/account.ts:182-184` (`setEetMode`): записує `eet_mode_changed_at` лише при справжній зміні режиму.
   - `lib/server/sales.ts:136-147` (`ingestSales`):
     - якщо `input.mode ≠ accountMode(account)` і `soldAt ≥ eet_mode_changed_at`, тржба йде в карантин `MODE_MISMATCH` (`retryable:false`, у `sales` нічого не пишеться, транспорт не викликається);
     - тржба з id, який уже є в `sales` цього акаунта, далі проходить звичну перевірку дубля/конфлікту;
     - тржби, продані до перемикання, зберігаються у своєму режимі (Р3, T8/T9).
   - **Рішення власника** (`lib/server/quarantine.ts:84-118`, API `ucet/karantena/[id]`, кнопки в `setup-app.tsx`):
     - «Odeslat v aktuálním režimu» (`send_current_mode`) повторно приймає тржбу з поточним режимом акаунта;
     - «Byla to zkouška» (`was_test`) закриває карантин як `dismissed` з поясненням; запис із повним payload лишається.

     Обидві дії дозволені лише для `MODE_MISMATCH`. Для цього коду кнопку «Zkusit znovu přijmout» сховано, бо вона знову дала б карантин.
   - **API:** відповіді `POST` і `GET /api/pokladna/sales` несуть `accountMode` (`api/pokladna/sales/route.ts`).
   - **Каса:**
     - `lib/pos/sync.ts:44-63,115,158,167`: при розбіжності `accountMode` з режимом у збереженій конфігурації каса позначає конфігурацію застарілою і одразу робить `refreshConfig()`. Крім того, конфігурація оновлюється в тику щонайменше раз на 5 хв (`CONFIG_REFRESH_MS`).
     - `lib/pos/sale-factory.ts`: поки конфігурація застаріла, нову тржбу створити не можна (зрозуміла помилка в платіжному вікні).
     - `components/pos/pos-app.tsx`: нова конфігурація застосовується одразу (не лише на `visibilitychange`), а поки вона застаріла, показується банер.
3. **Гейти, що були червоними** (`test/integration/r5-1-mode-mismatch.test.ts`):
   - **гейт:** перемикання в production у `t0`, тржба `mock` з `soldAt = t0 + 1 min` → `quarantined`, `MODE_MISMATCH`, 0 викликів транспорту. Було `expected { ok: true … } to match object { ok: false, quarantined: true … }`.
   - `setEetMode` записує час: `Cannot read properties of undefined (reading 'getTime')`.
   - рішення власника: `Tržba v karanténě neexistuje`.
   - `accountMode` у відповідях: `expected undefined to be 'production'`.

   Тепер усі зелені, разом із юніт-тестом `accountModeChanged` у `test/pos-sync-result.test.ts`. Тест «тржба до перемикання лишається у своєму режимі» зелений і до, і після: це контроль T9.
4. **Самостійні рішення:**
   - **T8/T9 (`r1-2-mode.test.ts`)** тепер явно задають порядок «продано за 10 хв до перемикання». Без цього вони залежали від того, чи потрапить `soldAt` у ту саму секунду, що й `now()` при створенні акаунта.
   - **«Byla to zkouška»** не зберігає тржбу як mock-тржбу (з фейковим POK), а закриває карантин із записом. Інакше пробна тржба потрапила б у денні підсумки й експорт як виручка.
   - **Перевірку режиму пропущено** для id, який уже є в `sales`. Інакше повторна синхронізація тржби, яку власник уже вирішив, знову відкривала б карантин; решту цього сценарію закриває R5.7.
   - **Повідомлення про розбіжність** називає обидва режими і час перемикання за празьким часом, щоб власник бачив, чому тржба в карантині.
5. **Що не вдалося:** —. UI каси (банер, блокування продажу) перевірено typecheck-ом і юніт-тестом логіки. Живого прогону в браузері для цього коміту не було.
