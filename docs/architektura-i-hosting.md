# Архітектура і хостинг EvidujZdarma

Документ відповідає на два питання:

- чи потрібен Supabase;
- де хостити: Hetzner чи чеський аналог.

Також тут описано, з чого складається система.

## Коротко

**Supabase не потрібен.** Усе працює на звичайному PostgreSQL 16 і власному коді на Next.js. Запускається одним `docker compose up` на будь-якому сервері в ЄС.

Рекомендований старт — один сервер **Hetzner Cloud** (Німеччина/Фінляндія, компанія з ЄС). Якщо згодом не хочеться адмініструвати базу, є два шляхи:

- перейти на керований PostgreSQL у ЄС;
- перейти на чеську PaaS **Zerops**.

Код міняти не доведеться: потрібен лише інший `DATABASE_URL`.

## Чому без Supabase

| Що дає Supabase | Що потрібно нам | Як зроблено |
| --- | --- | --- |
| Керований Postgres | Postgres | PostgreSQL 16 у Docker + щоденні бекапи (`infra/backup.sh`) |
| Auth (логін, сесії) | Вхід власника e-mailом; PIN касира, що працює офлайн | Magic-link + сесії в БД (`apps/web/src/lib/server/auth.ts`); PIN через PBKDF2 (перевірка в браузері без мережі) |
| Storage (файли) | Сертифікати .p12 | Не файли: приватний ключ шифрується (envelope encryption) і зберігається в БД |
| Realtime | Статус POK на касі | Каса синхронізується сама (офлайн-черга); realtime не потрібен |
| Edge Functions / cron | Повтор відправки тржб, листи, нагадування | `worker` викликає `/api/internal/cron` щохвилини |
| Автоматичний REST + RLS | Чіткий API з бізнес-правилами | Власні API-маршрути з валідацією (zod) |

Причини не брати Supabase:

1. **Дані й ключі.** Специфікація вимагає, щоб «дані тржб і ключі не виходили за межі ЄС». Supabase — компанія зі США. Регіон у Франкфурті розташований в ЄС, але на провайдера поширюється американський CLOUD Act. Для приватних ключів касових сертифікатів і податкових даних краще, щоб і провайдер був з ЄС.
2. **Вартість каталогу.** У каталозі фірм будуть сотні тисяч, а з часом мільйони рядків. До цього додаються ISR-сторінки і краулери. На Supabase за це платять розміром БД і egress-трафіком. На власному сервері — фіксовано, від ~15–40 €/міс.
3. **Офлайн-каса і фіскальне ядро** однаково потребують власного сервера: SOAP-підпис, черга, ключі. Supabase цю частину не закриває.
4. **Немає vendor lock-in.** Звичайний Postgres + Drizzle переноситься куди завгодно, включно із самим Supabase Postgres, якщо колись знадобиться.

n8n можна підняти поруч у тому ж Docker для маркетингових автоматизацій (CRM, розсилки). Обов'язкові листи вже вбудовані в застосунок: підтвердження реєстрації, чеки, нагадування.

## Де хостити

### Рекомендація: Hetzner Cloud (старт)

- Сервер **CCX13** (2 виділені vCPU, 8 ГБ) або **CPX31** у Falkenstein/Nürnberg. Затримка до Праги ~10 мс.
- **Hetzner Storage Box** (від ~4 €/міс) для офсайт-копій бекапів (restic/rclone).
- Hetzner Object Storage (S3) — якщо знадобляться файли, наприклад фото провозовен.
- Плюси: найкраща ціна/продуктивність, компанія з ЄС, проста адміністрація.
- Мінус: керованого Postgres немає, базу адмініструємо самі. Бекапи вже налаштовані.

### Чеські варіанти

| Провайдер | Що це | Коли брати |
| --- | --- | --- |
| **Zerops** (zerops.io, група VSHosting, Чехія) | PaaS: керований PostgreSQL з HA, Node.js-сервіси, бекапи, автоскейлінг | Коли не хочеться адмініструвати сервер і БД. Найближче до «Supabase без Supabase», але чеське |
| **VSHosting** (Прага) | Керовані сервери / Kubernetes з підтримкою 24/7 | Коли бізнес виросте і потрібні SLA та адміністратори |
| **WEDOS** (Глубока-над-Влтавоу) | Дешеві VPS / WEDOS Cloud | Бюджетний чеський VPS — той самий docker compose |
| **Master Internet** (Брно), **Forpsi**, **Active24** | VPS / dedicated | Альтернатива VPS у ЧР |

Наш стек — Docker + Postgres, тож переїзд між провайдерами означає перенести дамп БД і змінити DNS.

Якщо згодом знадобиться **керований Postgres у ЄС** без переїзду застосунку:

- **UpCloud** (Фінляндія);
- **Scaleway** (Франція);
- **OVHcloud** (Франція);
- **Aiven** (Фінляндія).

### Ключ шифрування сертифікатів (KMS)

- На старті використовується `MASTER_KEY` у змінних середовища сервера. Його треба зберігати окремо: у менеджері паролів, поза бекапами.
- Інтерфейс `KeyEncryptor` (`packages/fiscal-core/src/envelope.ts`) готовий до заміни на зовнішній KMS без зміни формату даних. Варіанти:
  - HashiCorp Vault / OpenBao Transit на окремій маленькій VM;
  - Scaleway Key Manager (ЄС).
- Ротація: можна додати `MASTER_KEY_v2` і встановити `MASTER_KEY_CURRENT=v2`. Старі ключі розшифровуються, нові шифруються новою версією.

### E-mail

Будь-який SMTP у ЄС через `SMTP_URL`:

- **Ecomail** (CZ) — зручно і для маркетингу;
- **Seznam Email Profi** (CZ);
- **Brevo** (FR);
- Postmark;
- AWS SES `eu-central-1`.

Для домену треба налаштувати SPF, DKIM і DMARC.

## Компоненти системи

```
apps/web            Next.js 16: сайт (SSR/SSG), API, PWA-каса (/pokladna), налаштування, онлайн-чеки
apps/worker         Планувальник: cron щохвилини, нагадування щогодини, нічне оновлення каталогу з ARES
packages/fiscal-core Фіскальне ядро EET 2.0 (спільне для каси, Alisio і B2B API)
packages/cz         Чеські утиліти: IČO, IBAN/рахунки, SPAYD QR, ARES-клієнт, CZ-NACE
packages/db         Схема Postgres (Drizzle) + міграції
infra/              docker-compose (Postgres, web, worker, Caddy HTTPS, бекапи)
```

### Потік тржби

1. Каса створює тржбу і **спочатку зберігає її в IndexedDB**. Номер (pořadové číslo) береться з локального лічильника з унікальним префіксом пристрою.
2. Синхронізація надсилає пакет на `/api/pokladna/sales` з токеном пристрою. Сервер ідемпотентний (UUID тржби), тож повтори безпечні.
3. Сервер одразу пробує відправити тржбу у Finanční správu:
   - SOAP v4.1, WS-Security, підпис ключем пристрою;
   - ключ розшифровується лише в пам'яті;
   - відповідь FS приймається тільки після перевірки її підпису і ланцюжка сертифікатів.
4. Якщо FS недоступна, тржба лишається в черзі. Worker повторює відправку з backoff: та сама ідентичність тржби, новий `uuid_zpravy`, `prvni_zaslani=false`. Так триває до отримання POK у межах 48 годин. Перед закінченням строку власник отримує лист.
5. Каса підтягує статус і POK і показує його на чеку. Чек можна роздрукувати, надіслати e-mailом або показати QR.

### Режими каси

- `mock` — демо, без FS.
- `playground` — тестове середовище FS.
- `production` — ostrý provoz.

Кожна тржба відправляється в тому режимі, в якому була створена.

### Що перевірено автоматичними тестами

- Канонікалізація і підпис збігаються побайтово з **офіційним підписаним зразком FS**.
- Справжня підписана відповідь Playground (21. 7. 2026) проходить перевірку; підроблений POK відхиляється.
- Envelope encryption, PKCS#12, SPAYD, IČO, рахунки/IBAN, ARES-мапери, оцінка «чи стосується EET», калькулятор EET OFF.
- E2E у браузері:
  - реєстрація пристрою;
  - PIN;
  - продаж з рештою;
  - **офлайн-продаж → автоматична відправка після відновлення мережі**.
